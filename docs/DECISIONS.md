# TransitOS Foundations — Decision Record

Every ruling made while executing the 23-task Foundations plan. Each records what was decided, why, and what it costs if the decision was wrong. Preserved here because the working ledger they came from was git-ignored scratch.

Branch: `foundations` · 49 commits · 162 unit/integration tests + 7 e2e · final whole-branch review clean.

## Still open — carried into later sub-projects

- **MFA challenge token is not single-use** (R44). Spec §4 requires single-use; it ships as a stateless 300s JWT. A redemption still requires a fresh valid TOTP, so exposure is bounded, but this must be closed before any MFA-dependent flow ships in Sub-project 2.
- **School deletion will collide with the audit FK** (R46c). `core.users.school_id` cascades from `core.schools`, and `audit_logs.actor_user_id` is now `ON DELETE NO ACTION` — so deleting a school with audit history fails loudly. The sub-project that adds a delete endpoint needs a documented purge/anonymise path.
- **RLS is a tenant boundary, never a role boundary.** `users_tenant_all` is `FOR ALL`, so at the RLS layer a `parent` or `driver` session has read and write rights over every user row in its own school. Safe today only because no endpoint exposes it. Do not assume otherwise.
- **Three auth tables carry no RLS by design** — `refresh_tokens`, `password_history`, `mfa_credentials` — because all three are read before a tenant or user context exists. Application-level `user_id` filtering is their only control.

### Ruling R15: the Important finding is CORRECT and gets fixed, despite being mandated by my own brief. In `bootstrap-db.ts`, `dbName` is parsed out of `DATABASE_MIGRATION_URL` and interpolated into `GRANT CONNECT ON DATABASE "${dbName}"`, but that variable is validated only as a generic URL — so the design's stated invariant ("DDL interpolation is safe because the value passed the sqlIdentifier regex") does not actually hold for it. — Why fix rather than park: `engineering-standards.md` §1 requires validation at boundaries, and the current safety rests on an incidental WHATWG-URL parser side effect (percent-encoding `"`), which is exactly the kind of implicit invariant that breaks silently when someone later swaps the parser or hand-builds the URL. Exploitability today is low (operator-controlled env var), which is why it is Important and not Critical. — Fix shape: extract an exported, unit-testable `databaseNameFromUrl(url: string): string` that decodes the path segment and validates it against `^[A-Za-z_][A-Za-z0-9_$]{0,62}$` (Postgres's 63-byte identifier cap), throwing a clear error otherwise. — Cost if wrong: a database legitimately named with characters outside that set would need the pattern widened; no runtime risk.
### Ruling R17: the Important finding is CORRECT and gets fixed. The "no tenant context" test never sets `app.current_school_id` at all, so `current_setting(...)` returns SQL NULL — and `NULL::uuid` is NULL with or without the NULLIF wrapper, meaning the test passes identically if NULLIF is deleted. The case NULLIF actually guards, an empty-string session variable, is untested. — Why this matters concretely: Task 11's interceptor sets `app.current_school_id = ''` for unauthenticated requests (`claims?.schoolId ?? ''`), so the empty-string path is the production path, not a hypothetical; without NULLIF it raises `invalid input syntax for type uuid: ""` and every unauthenticated request 500s. A regression here would be invisible to the current suite. — Fix: add a test that sets `app.current_school_id = ''` explicitly with is_super_admin false and asserts 0 rows returned rather than an error. — Cost if wrong: one extra test.
### Ruling R19: Task 5's "auth lookup flag has no write power" test asserts `expect(result[1]).toBe(0)` on the raw return of a TypeORM `query()` UPDATE. That shape is driver- and version-dependent (TypeORM's postgres driver does not reliably return `[rows, affectedCount]` across versions), so the test could pass or fail for reasons unrelated to RLS. Replace it with a semantic assertion: attempt the UPDATE under the auth-lookup context, then re-read the row under a super_admin context and assert the value is unchanged. — Why: the property under test is "the carve-out grants no write power", and that must be proven by observing the data, not by trusting an ORM return shape. — Cost if wrong: none; the semantic form is strictly stronger.
### Ruling R20: promote Task 8's first Minor to an immediate fix, against the usual rule that minors are deferred to the final review. The tamper test's guard `ciphertext.slice(-2) === 'AA' ? 'BB' : 'AA'` compares against UPPERCASE hex, but Buffer.toString('hex') always emits lowercase — so the ternary always yields 'AA', and because Buffer.from(hex) parsing is case-insensitive, a payload whose final byte is already 0xaa produces a tampered string that decodes to identical bytes. Decryption then succeeds and `expect(...).toThrow()` fails: a ~1/256 flake. — Why fix now rather than defer: 15 tasks remain, each running the full suite at least twice, so this has roughly an 11% chance of producing a spurious failure that would send an implementer or reviewer chasing a non-existent bug mid-run; and Task 13 builds directly on this module, which the reviewer also flagged. The severity classification stands (the encryption itself is correct) — this is a scheduling decision about operational cost, not a re-grading. — Cost if wrong: one small extra fix round.
### Ruling R25: the Important finding is CORRECT and gets fixed, despite originating in my own brief. `verifyAccessToken` performs no discriminant check, so an MFA challenge token — signed with the same JWT_SECRET — verifies successfully and is returned typed as AccessTokenClaims with role/schoolId/isSuperAdmin actually `undefined` at runtime. — Why this matters concretely: the challenge token is issued AFTER the password check but BEFORE the second factor, so accepting it as a bearer credential defeats the point of MFA. Blast radius is partial rather than total (Task 11 would stamp an empty tenant context and Task 15's RolesGuard would reject any @Roles route), but routes carrying no @Roles decorator — /users/me, /auth/logout, /auth/logout-all — would admit a half-authenticated caller who never completed MFA. It also silently violates the non-optional fields of the interface's own contract, feeding undefined into RLS session-variable stamping. — Fix shape: positive discriminant rather than negative. signAccessToken embeds `purpose: 'access'`; verifyAccessToken requires it and returns the four public claim fields unchanged, so AccessTokenClaims stays a 4-field contract and Tasks 11/15/16 need no changes. A positive check also fails safe if a third token type is ever added, where a "reject if purpose === mfa-challenge" check would silently admit it. — Cost if wrong: tokens minted before the change would not verify; none exist outside tests.
### Ruling R27: fix the Important finding — `queryRunner.connect()` and `startTransaction()` sit outside the try/finally, so a connection acquired by connect() is never released if startTransaction() throws (dropped connection, DB overload). Plan-mandated, verbatim from my brief. — Why it matters: this is the keystone request path; a leaked pool connection per failed transaction is a slow production outage under exactly the load conditions that cause the failure. — Cost if wrong: none, the fix is moving two lines inside try.
### Ruling R28: promote Task 11's first Minor to the same fix round. Replace the interpolated `SET LOCAL app.current_school_id = '${...}'` with `SELECT set_config('app.current_school_id', $1, true)` using a bound parameter. — Why promote rather than defer: it sits on the keystone security path, costs one line, and permanently removes an injection class instead of relying on the invariant that schoolId is always a DB-generated UUID from a verified JWT. That invariant holds today, which is why the reviewer rated it Minor; the point of fixing now is that nothing downstream has to keep holding it. — Cost if wrong: none; set_config with `is_local = true` is exactly equivalent to SET LOCAL.
### Ruling R29: fix Important #1 — the revokeAllForUser test cannot detect the regression it exists to catch. The spec seeds exactly one user, so if the `WHERE user_id = :userId` clause were dropped and the method wiped EVERY user's refresh tokens, the suite would still pass. core.refresh_tokens has no RLS by design, so application-level filtering is the only control on that table and the test suite is the only thing that can catch its removal. — Fix: seed a second user and assert their token still rotates after revokeAllForUser is called for the first. — Cost if wrong: one extra fixture.
### Ruling R30: fix Important #2 — rotate() is a read-then-update (findOne, validity check, separate update), so two concurrent presentations of the same still-valid token can both pass validation before either update commits, each minting a fresh token pair. That defeats the single-use invariant under exactly the replay scenario rotation exists to limit. No sequential Jest suite can expose it; it is structural, not a coverage gap. — Fix: make the revoke a single atomic statement carrying the validity predicate (UPDATE ... WHERE token_hash = $1 AND revoked_at IS NULL AND expires_at > now() AND device_fingerprint = $2 RETURNING *) and proceed only when exactly one row was affected. — Cost if wrong: none; the atomic form is strictly stronger and keeps the same rejection semantics.
